# ansible-role-kafka

[English](README.md) | Русский

Ansible-роль, которая разворачивает и сопровождает кластер Apache Kafka в
режиме KRaft на RED OS 8 из RPM-пакета дистрибутива. Каждый хост группы
инвентаря `kafka` работает одновременно как брокер и контроллер.

Автор: Nikita Grabar. Copyright (c) 2026 Nikita Grabar. All rights reserved.
См. [COPYRIGHT](COPYRIGHT).

## Область применения

Роль:

- устанавливает строго `apache-kafka-3.9.1-1.red80`;
- записывает `server.properties` и systemd-unit KRaft вместо пакетных;
- останавливает, отключает и маскирует пакетный `zookeeper.service`;
- однократно, при инициализации нового кластера, форматирует хранилище и
  записывает запись владения;
- в последующих прогонах применяет свою конфигурацию к кластеру, который
  она инициализировала, и при необходимости перезапускает узлы по одному.

Роль не делает следующего:

- не генерирует cluster ID;
- не принимает под управление существующие установки Kafka и данные;
- не исправляет частичную инициализацию и не восстанавливает хосты
  автоматически;
- не меняет cluster ID, node ID, состав контроллеров и путь хранения
  инициализированного кластера, не заменяет узлы;
- не обновляет Kafka до другой версии;
- не настраивает TLS, аутентификацию, ACL, репозитории пакетов и firewalld.

## Требования

### Управляемые хосты

- RED OS 8 с systemd. Принимаются хосты, у которых `ansible_distribution`
  равно `RED` или `REDOS`, а основная версия — `8`.
- IPv4-маршрут по умолчанию. Адрес интерфейса маршрута по умолчанию
  (`ansible_default_ipv4.address`) используется для listeners и голосующих
  контроллеров кворума и должен быть уникален в группе.
- Настроенные репозитории RED OS, предоставляющие `apache-kafka-3.9.1-1.red80`
  (в проверенном окружении пакет брался из репозитория `updates`). Роль
  запрашивает только эту версию-релиз и не добавляет репозитории.
- Java явно не устанавливается. Пакет требует `java-11-openjdk-devel`, и dnf
  ставит его как зависимость.
- Открытые между всеми участниками группы TCP 9092 (брокер) и 9093
  (контроллер).
- Повышение привилегий до root.

### Управляющий узел

- Роль проверена на ansible-core 2.13.13 (Python 3.10, Jinja2 3.1.6) с
  `jinja2_native = False` по умолчанию. Другие версии не проверялись.
- Используются только модули и фильтры `ansible.builtin`, коллекции не нужны.

## Топология и соединения

- `process.roles=broker,controller` на каждом хосте группы `kafka`.
- `controller.quorum.voters` перечисляет всех участников группы как
  `<node_id>@<IPv4 по умолчанию>:9093` в порядке node ID.
- Listeners: `PLAINTEXT://<IPv4 по умолчанию>:9092` для клиентов и брокеров и
  `CONTROLLER://<IPv4 по умолчанию>:9093`, отображённый на `PLAINTEXT`.
- Все соединения без шифрования и аутентификации. Ограничивайте сетевой доступ
  к этим портам вне роли.
- Параметры репликации зависят от размера группы *n*:
  - `default.replication.factor`, `offsets.topic.replication.factor` и
    `transaction.state.log.replication.factor` — min(3, n);
  - `min.insync.replicas` и `transaction.state.log.min.isr` — min(2, n).

## Переменные

Обязательны две переменные инвентаря, значений по умолчанию нет.

| Переменная | Уровень | Требование |
|---|---|---|
| `kafka_cluster_id` | группа | 22-символьный cluster ID Kafka (`^[A-Za-z0-9_-]{22}$`), одинаковый на всех хостах, сравнивается с учётом регистра |
| `kafka_node_id` | хост | целое от 0 до 2147483647, уникальное в группе и неизменное всё время жизни хоста |

Cluster ID сгенерируйте один раз, до установки Kafka на управляемые хосты.
Например, выполните на управляющем узле:

```sh
python3 -c 'import uuid,base64; print(base64.urlsafe_b64encode(uuid.uuid4().bytes).decode().rstrip("="))'
```

Другой вариант — `/opt/kafka/bin/kafka-storage.sh random-uuid` на любом хосте,
где пакет уже установлен.

Сохраните полученное значение как `kafka_cluster_id` и храните его после
инициализации. После инициализации не меняйте ни его, ни node ID.
Роль отказывает при таких изменениях, а также при смене IPv4-адреса маршрута
по умолчанию у хоста, потому что это меняет состав контроллеров.

### Фиксированные константы

В `vars/main.yml` заданы фиксированные константы:

- имя пакета и версия-релиз;
- порты 9092 и 9093;
- `/opt/kafka` (домашний каталог, `config/server.properties`, `logs`);
- `/etc/systemd/system/kafka.service`;
- `/var/lib/kafka` (каталог состояния, каталог хранения `data` и запись
  владения `ansible-kafka-owner.json`).

Переменные роли из `vars` имеют приоритет над переменными инвентаря, поэтому
инвентарь не может изменить эти константы. Переопределение другим способом,
например через extra vars, не поддерживается и не проверялось.

Поддерживаемая настройка ограничена составом группы `kafka` в инвентаре и
двумя переменными выше. Другие изменения конфигурации требуют изменения самой
роли.

## Установка и использование

Поместите роль в `roles/kafka/` родительского Ansible-проекта, чтобы play
находил её по имени `kafka`:

```text
project/
├── inventory.yml
├── kafka.yml
└── roles/
    └── kafka/        # содержимое этого репозитория
```

Например, клонируйте этот репозиторий в `roles/kafka`:

```sh
git clone https://github.com/slenderchat/ansible-role-kafka.git roles/kafka
```

Минимальный инвентарь (`inventory.yml`):

```yaml
all:
  children:
    kafka:
      hosts:
        kafka-1.example.com:
          kafka_node_id: 1
        kafka-2.example.com:
          kafka_node_id: 2
        kafka-3.example.com:
          kafka_node_id: 3
      vars:
        kafka_cluster_id: "<22-символьный cluster ID>"
```

Плейбук (`kafka.yml`). Сообщения об ошибках роли ссылаются на него по этому
имени.

```yaml
- name: Deploy Kafka cluster
  hosts: kafka
  become: true
  gather_facts: true
  strategy: linear
  any_errors_fatal: true
  roles:
    - role: kafka
      tags: [always]
```

Запуск из каталога родительского проекта:

```sh
ansible-playbook -i inventory.yml kafka.yml
```

### Ограничения запуска

Проверки preflight останавливают play на всех хостах до изменений, если не
выполнено хотя бы одно из условий:

- play нацелен ровно на группу `kafka` одним пакетом (без `--limit` и без
  `serial`);
- запуск не в режиме проверки (`--check`);
- не заданы `--tags` и `--skip-tags`;
- выполнены требования к платформе выше;
- переменные корректны, node ID и адреса уникальны, а cluster ID одинаков на
  всех хостах.

Некоторые параметры не обнаруживаются:

- `--start-at-task` и `--step`;
- `--skip-tags always`, при котором вся роль пропускается без изменений.

Не используйте их.

## Поведение

### Фазы прогона

Каждый прогон выполняет на всей группе фазы:

1. preflight;
2. инспекция только для чтения;
3. групповая валидация;
4. конфигурация;
5. инициализация (только для нового кластера);
6. запуск и перезапуск сервиса.

Первые три фазы не меняют хосты. Благодаря `strategy: linear` и
`any_errors_fatal: true` сбой на любом хосте останавливает play до фазы
конфигурации.

### Граница инспекции

Инспекция читает только настроенные пути и сервисы:

- установленную версию `apache-kafka` и результаты `rpm -V` для
  `/opt/kafka/config/server.properties` и `/etc/systemd/system/kafka.service`;
- наличие этих двух файлов, если пакет не установлен;
- `kafka.service`: состояние, включение, drop-in'ы в `kafka.service.d`, время
  старта основного процесса и ожидающий reload;
- `zookeeper.service`: состояние, включение и состояние загрузки;
- работающие процессы `kafka.Kafka`;
- запись владения `/var/lib/kafka/ansible-kafka-owner.json`;
- `/var/lib/kafka/data`: наличие, тип, полный листинг и `meta.properties`.

Данные Kafka в других местах, например в пакетных путях по умолчанию в `/tmp`,
не обнаруживаются.

Если листинг существующего каталога данных пропущен или сообщает о путях,
которые не удалось прочитать, play останавливается до изменений.

### Состояния хостов и решение по группе

Каждый хост относится к одному из четырёх состояний:

- **clean** — в пределах инспектируемой области нет признаков, мешающих
  инициализации.
  - Пакет отсутствует и файлов по настроенным путям нет, либо установлена
    точная версия и оба управляемых файла не изменены.
  - `kafka.service` не активен, не включён и не имеет drop-in'ов Kafka,
    процесс Kafka не запущен.
  - ZooKeeper не активен и не включён.
  - Записи владения нет.
  - Каталог данных отсутствует или пуст.
- **owned** — инициализирован этой ролью и согласован с текущими переменными.
  - Запись совпадает: создана этой ролью, с тем же cluster ID, тем же
    целочисленным node ID, тем же путём хранения и теми же голосующими
    контроллерами.
  - Установлена точная версия пакета.
  - Drop-in'ов Kafka нет.
  - Не обнаружен процесс сервера Kafka при неактивном `kafka.service`.
    Проверка не определяет, какому сервису принадлежит процесс, и не
    обнаруживает дополнительный процесс Kafka при активном сервисе.
  - В каталоге данных есть `meta.properties` с теми же `cluster.id` и
    `node.id`.
- **inconsistent** — запись владения есть, но хост от неё отклоняется.
- **unowned** — следы Kafka без записи, устанавливающей владение ролью.

Группа продолжает только в двух случаях:

- **все хосты clean** — инициализация нового кластера;
- **все хосты owned** — применение конфигурации.

Любое другое сочетание отклоняется до изменений с отчётом по каждому хосту.
Примеры: смесь clean и owned, либо хотя бы один хост inconsistent или unowned.

### Инициализация

Когда вся группа clean, роль:

1. устанавливает пакет и записывает конфигурацию;
2. выполняет на каждом хосте `kafka-storage.sh format` с заданным cluster ID
   (без `--ignore-formatted`);
3. записывает запись владения на хосте только после успешного форматирования
   на нём;
4. запускает все узлы одной задачей;
5. выполняет проверки готовности на запущенных узлах.

Инициализация не атомарна по хостам.

### Перезапуски и проверки готовности

Работавший узел перезапускается, если выполняется одно из условий:

- этот прогон изменил `server.properties` или unit;
- любой из этих файлов изменён после старта основного процесса Kafka. Время
  сравнивается в целых микросекундах, поэтому перезапуск, отложенный
  прерванным прогоном, не теряется. Смена времени изменения файла без
  изменения содержимого тоже вызывает перезапуск.

Остановленные узлы запускаются, а не перезапускаются.

Если перезапуск нужен хотя бы одному узлу:

1. сначала все узлы проходят проверки готовности;
2. отмеченные узлы перезапускаются по одному в порядке node ID;
3. каждый перезапущенный узел проходит проверки готовности до перезапуска
   следующего.

Перед каждым перезапуском роль также отказывается продолжать, если участник
группы уже завершился с ошибкой или стал недоступен в этом прогоне.

Проверки готовности выполняются на узле с этого же узла:

- его собственные порты 9093 и 9092 принимают соединения (до 300 с);
- порты 9093 и 9092 всех участников группы доступны (по 60 с на адрес);
- `kafka-metadata-quorum.sh describe --replication` показывает node ID как
  Leader или Follower с lag 0;
- `kafka-broker-api-versions.sh` показывает node ID;
- `kafka-topics.sh --describe --under-replicated-partitions` возвращает пустой
  результат.

Проверки готовности выполняются только на узлах, запущенных в этом прогоне, и
вокруг поочерёдных перезапусков. Прогон, который ничего не запускает и не
перезапускает, здоровье кластера не проверяет. Состояние fencing брокеров
явно не проверяется.

### Unit'ы systemd и ZooKeeper

Пакет устанавливает свои `kafka.service` и `zookeeper.service` обычными
файлами в `/etc/systemd/system`. Пакетный `kafka.service` требует ZooKeeper, и
drop-in эту зависимость убрать не может.

Поэтому роль:

- заменяет `/etc/systemd/system/kafka.service` своим unit'ом KRaft, так что
  `rpm -V` показывает файл изменённым;
- загружает новый unit, затем останавливает и отключает `zookeeper.service`;
- маскирует ZooKeeper заменой его файла ссылкой на `/dev/null`, потому что
  `systemctl mask` не заменяет обычный файл в `/etc/systemd/system`;
- выполняет `systemctl daemon-reload`, когда маска изменилась или когда в
  systemd всё ещё загружено определение, отличное от маски.

Остановленный ZooKeeper может отображаться как `failed`, потому что пакетный
unit не считает код выхода 143 успешным. Роль никогда не снимает маску
ZooKeeper.

Ранее при переустановке `apache-kafka-3.9.1-1.red80` наблюдалось следующее:

- пакетные файлы `kafka.service` и `zookeeper.service` восстанавливаются, маска
  снимается;
- `server.properties` сохраняется;
- скриптлет пакета сразу перезапускает `kafka.service` с пакетным unit'ом,
  который запускает ZooKeeper.

Этот перезапуск происходит вне роли. Если точную поддерживаемую версию пакета
нужно переустановить, делайте это по одному узлу, затем запускайте роль.
Следующий прогон рассчитан на восстановление unit'а роли и маски и перезапуск
затронутого узла. Это согласование не повторялось после последнего изменения
условия reload для ZooKeeper (см. «Проверка»).

### Восстановление после прерванного первого развёртывания

Окно ручного восстановления начинается, когда первый прогон записывает
`server.properties`, а не когда он форматирует хранилище. Если первый прогон
остановился раньше, чем каждый хост отформатирован и получил запись владения,
последующие прогоны классифицируют затронутые хосты как unowned (или
inconsistent) и отказываются продолжать.

Роль это состояние не исправляет. Чтобы повторить развёртывание, верните все
хосты в описанное выше состояние clean:

- нет записи владения и содержимого в `/var/lib/kafka/data`;
- `kafka.service` остановлен и отключён, процесс Kafka не запущен;
- `/opt/kafka/config/server.properties` и `/etc/systemd/system/kafka.service`
  либо не изменены по `rpm -V`, либо отсутствуют вместе с пакетом.

Затем снова запустите плейбук. Делайте это только для кластера без нужных
данных, потому что хранилище при этом теряется.

## Проверка

Текущий код проверен на тестовой группе из трёх хостов RED OS 8.0.3 с
systemd 253, сообщающих `RED`. На управляющем узле был
ansible-core 2.13.13 с `jinja2_native = False`.

Наблюдавшиеся результаты:

- **Отказы до изменений на чистой группе.** Play останавливался до изменений,
  когда:
  - cluster ID одного хоста отличался только регистром букв;
  - файл конфигурации или файл unit'а оставался без пакета.
- **Инициализация с чистых хостов.**
  - Сформировался кворум 3/3 с нулевым lag и тремя брокерами.
  - Топик с тремя партициями, фактором репликации 3 и
    `min.insync.replicas=2` принял сообщения с `acks=all`, все сообщения были
    прочитаны.
- **Прогоны без изменений.** Повторные прогоны давали `changed=0` без
  форматирования, перезаписи записи владения, daemon reload и перезапусков.
- **Точность времени старта.**
  - Файл, изменённый раньше старта процесса в ту же секунду, перезапуска не
    вызывал.
  - Файл, изменённый позже в ту же секунду, вызывал перезапуск, и только на
    этом узле.
- **Прерванный прогон.** После прогона, остановленного сразу после записи
  конфигурации, следующий прогон перезапустил все узлы по одному в порядке
  node ID.
- **Отказы на инициализированном кластере.** Play останавливался до изменений
  в следующих случаях:
  - логический или дробный node ID в записи владения (inconsistent);
  - удалённая запись владения (unowned);
  - отсутствующий или противоречивый `meta.properties` (inconsistent);
  - один clean-хост рядом с owned-хостами.
- **Отложенная маска ZooKeeper.** ZooKeeper работал с пакетным unit'ом, а его
  файл был заменён маской без reload. Роль остановила ZooKeeper, выполнила
  reload systemd, и ZooKeeper стал masked. Kafka не перезапускалась.

Не проверено при выполнении:

- **Неполный листинг каталога данных.** Этот сценарий внесения сбоя не
  выполнялся: в тестовом окружении root читал каталог без ошибок. Условие
  остановки опирается на поведение `ansible.builtin.find` в
  ansible-core 2.13.13, подтверждённое чтением исходного кода модуля, а не
  прогоном.
- **Переустановка пакета.** Переустановка точной версии пакета и последующее
  согласование проверялись до последнего изменения условия reload для
  ZooKeeper. Согласование с тех пор не повторялось.
- **Другие окружения и сбои:**
  - хосты, сообщающие `REDOS`;
  - размер группы, отличный от трёх;
  - другие версии ansible-core;
  - активный firewalld;
  - потеря узла во время цикла поочерёдных перезапусков.
